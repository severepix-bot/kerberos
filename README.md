# Assistente local

Agente operacional de terminal que usa o modelo aberto **Qwen 2.5 3B** localmente pelo Ollama. O **LangGraph** coordena agentes especialistas e chamadas encadeadas de ferramentas: para pedidos executáveis, o Cérebro seleciona ferramentas carregadas, age dentro das permissões e verifica o resultado em vez de apenas explicar como fazer. Menções como `@cloudflare` direcionam a tarefa às ferramentas MCP daquele plugin somente quando estão conectadas; pedidos sobre GitHub também priorizam as ferramentas GitHub MCP carregadas. Diagnósticos de autenticação e acesso devem refletir os resultados reais dessas chamadas, não hipóteses; nomes de ferramentas e operações não são inventados. Opcionalmente, o Cerebro consulta em paralelo hubs externos configurados (OpenHands, OpenRouter, GitHub Copilot CLI, CrewAI AMP e AutoGen Studio) e usa o Ollama para sintetizar as respostas. Hubs externos exigem autenticação própria e podem cobrar pelo uso.

Os pesos do modelo não são distribuídos nesta pasta: o Ollama baixa e armazena o modelo no computador na primeira execução, após confirmação. O arquivo `modelo/modelo.json` registra o modelo recomendado.

## Requisitos

- Python 3.10 ou superior
- Node.js/npm para os plugins MCP incluídos
- [Ollama](https://ollama.com/download) instalado e em execução
- macOS ou Windows para controle de aplicativos; navegador e MCP também funcionam em Linux

## Iniciar pelo terminal

1. Instale e abra o Ollama.
2. No terminal, entre nesta pasta e execute o comando de inicialização:

   - macOS/Linux: `./cerebro`
   - Windows: `cerebro.bat`

O comando `./cerebro` inicia o assistente dentro desta pasta. Se preferir, os lançadores originais também continuam disponíveis: `./iniciar.sh` e `iniciar.bat`.

O cliente remoto usa `https://cerebrocentra.com` como padrão para `CEREBRO_SERVER_URL`; defina essa variável para outra URL se necessário. A conexão ainda exige `CEREBRO_API_TOKEN`.

Ao iniciar o modo interativo local, o cliente pode enviar em segundo plano um relatório mínimo de sintaxe Python para `POST /v1/improvements`; não envia código, nomes de arquivos ou mensagens de erro. O upload só ocorre quando `CEREBRO_IMPROVEMENTS_UPLOAD_TOKEN` está configurado com o mesmo segredo aleatório de pelo menos 32 caracteres no cliente e no servidor (gere um com `openssl rand -hex 32`). Esse token é separado de `CEREBRO_API_TOKEN`. Se o domínio usar Cloudflare Access, configure um Service Token para a rota `/v1/improvements` e defina `CEREBRO_CF_ACCESS_CLIENT_ID` e `CEREBRO_CF_ACCESS_CLIENT_SECRET` no cliente; não desative Access para o restante do site. O servidor armazena localmente apenas os relatórios agregados em `improvements.sqlite3`, limita cada token a um upload por minuto e mantém no máximo os 1.000 mais recentes; payloads grandes ou com campos adicionais são rejeitados. A configuração do DNS/Cloudflare Access e a implantação do servidor são etapas externas; os arquivos deste projeto não alteram sua conta Cloudflare.

Para trabalhar em outro projeto, defina `CEREBRO_PROJECT_ROOT` com o caminho absoluto da pasta antes de iniciar. A pasta precisa existir e conter um marcador de projeto conhecido (`.git`, `package.json`, `pyproject.toml`, `README.md` ou equivalente); a raiz do disco e a pasta home não são aceitas:

```sh
CEREBRO_PROJECT_ROOT="/Users/italosantos/Desktop/www-italosantos-com" ./cerebro
```

As ferramentas de arquivos e os processos do terminal usam essa raiz durante a execução. O diretório dos arquivos do próprio Cerebro, seu ambiente Python e as configurações MCP incluídas continuam vinculados à instalação do assistente. A seleção vale para o processo do servidor; no modo remoto, configure a variável no servidor, pois processos e arquivos são acessados nele. A raiz restringe as ferramentas de arquivos e o diretório de trabalho, mas **não é um sandbox para comandos**: processos autorizados pelo usuário podem acessar outros arquivos permitidos pela conta do sistema operacional.

Ao iniciar uma conversa, o terminal é limpo e exibe um grande anel ciano centralizado, com “CEREBRO   CENTRAL” em ciano brilhante logo abaixo. A entrada aparece com o usuário e o nome do computador (por exemplo, `italosantos@macbook>`); cada resposta do Cerebro Central aparece abaixo dentro de uma caixa ciano. O aviso de inicialização aparece em amarelo. As cores e a limpeza da tela são usadas apenas em terminais interativos.

O script cria um ambiente virtual, instala as dependências e instala o Chromium do Playwright. Na primeira inicialização, confirme o download do modelo (aproximadamente alguns GB). Também é possível baixá-lo manualmente com `ollama pull qwen2.5:3b`.

Para trocar o modelo, defina `OLLAMA_MODEL` no ambiente antes de iniciar. Para usar outro servidor Ollama, defina `OLLAMA_HOST` (por exemplo, `http://127.0.0.1:11434`).

## Fine-tuning local do modelo

Em Macs Apple Silicon, `mlx-lm` cria um adaptador LoRA separado, sem modificar os pesos-base. No modo geral, usa pares de mensagem do usuário e resposta final do assistente das conversas locais importadas e dos históricos legíveis do VS Code/Codex. Para incluir a trilha de um projeto específico — pedidos, chamadas de ferramentas/comandos, resultados/erros e respostas finais — treine com `--project-name <pasta>`. Nesse modo, o comando seguinte e a resposta final recebem o histórico de execução como contexto, com estados de erro explícitos; somente rollouts cujo workspace termine exatamente com o nome solicitado são usados. Os rollouts são lidos diretamente sem reindexar eventos no banco de histórico. Padrões comuns de credenciais, e-mail, IP e caminhos do usuário são removidos, exemplos repetidos são eliminados e treino/validação/teste são separados por sessão. A redação é baseada em padrões e não garante a remoção de todo dado sensível. Os dados sanitizados e adaptadores ficam em `CEREBRO_TRAINING_DIR` quando definido; caso contrário, em `CEREBRO_DATA_DIR/training` (por padrão `~/.local/share/cerebro/training`). Ambos recebem permissões privadas; os históricos originais não são modificados nem enviados a serviços externos.

Instale o treinador em um ambiente Python isolado e prepare os dados:

```sh
python3.13 -m venv ~/.local/share/cerebro/training-venv
~/.local/share/cerebro/training-venv/bin/python -m pip install mlx-lm
~/.local/share/cerebro/training-venv/bin/python -m assistente.training prepare
```

Para treinar um adaptador LoRA com os dados locais atuais:

```sh
~/.local/share/cerebro/training-venv/bin/python -m assistente.training train
```

Para condicionar pares reais de conversa às notas relevantes de longo prazo:

```sh
~/.local/share/cerebro/training-venv/bin/python -m assistente.training train --include-learnings
```

O treinamento continua sendo iniciado explicitamente; guardar uma orientação não dispara downloads nem fine-tuning automático. Notas sozinhas não são pares de treino: essa opção inclui orientações relevantes no contexto de exemplos reais correspondentes, não inventa respostas. Revise os dados sanitizados antes do fine-tuning. O resultado é um adaptador LoRA separado; o Cérebro/Ollama não altera nem carrega automaticamente os pesos-base ou o adaptador.

Também é possível treinar localmente com as bibliotecas do Hugging Face (Transformers, TRL e PEFT), em vez de MLX. Esse backend mantém os mesmos dados locais e sanitizados, converte cada par para prompt/completion e calcula loss somente sobre a completion do assistente. Não exige token Hugging Face para o modelo público padrão e não publica nem envia os dados ou adaptador ao Hub.

```sh
~/.local/share/cerebro/training-venv/bin/python -m pip install -r requirements-training-hf.txt
~/.local/share/cerebro/training-venv/bin/python -m assistente.training prepare
```

Inspecione os arquivos `train.jsonl`, `valid.jsonl` e `test.jsonl` no caminho exibido antes de iniciar o treinamento. O backend exige que você passe explicitamente o caminho revisado e só aceita datasets preparados no diretório privado de treinamento; não recolhe históricos por conta própria:

```sh
~/.local/share/cerebro/training-venv/bin/python -m assistente.training train-hf --dataset "$HOME/.local/share/cerebro/training/datasets/TIMESTAMP"
```

Por padrão, o backend usa `Qwen/Qwen2.5-0.5B-Instruct` e grava um novo adaptador em `adapters/`. É possível selecionar outro modelo compatível com Transformers/TRL via `--model <id-ou-caminho-local>`. O treino usa o split `train`, a validação seleciona checkpoints e o split `test` só é avaliado após o treino. O tamanho de memória necessário depende do modelo e do hardware; esse caminho usa precisão adequada ao dispositivo detectado, sem QLoRA. Embora os arquivos fiquem locais, padrões de sanitização não detectam todo dado sensível; revise o dataset antes de treinar. O adaptador PEFT não é carregado pelo runtime Ollama e não muda o modelo ativo do Cérebro.

Para treinar especificamente com comandos/resultados/erros e respostas finais dos rollouts de `www-italosantos-com`:

```sh
export CEREBRO_TRAINING_DIR="$PWD/training"
~/.local/share/cerebro/training-venv/bin/python -m assistente.training train --project-name www-italosantos-com
```

O treinamento baixa `mlx-community/Qwen2.5-3B-Instruct-4bit` do Hugging Face quando necessário e treina uma época com validação e teste. Cada execução produz um adaptador novo; não substitui nem modifica o modelo Ollama original. Para carregar um adaptador no servidor MLX-LM, use `mlx_lm.server --model mlx-community/Qwen2.5-3B-Instruct-4bit --adapter-path ~/.local/share/cerebro/training/adapters/<adaptador> --host 127.0.0.1 --port 8080`. O runtime do Cérebro deste projeto continua configurado para Ollama e não troca automaticamente para o adaptador treinado. O treinamento e o uso dos pesos Qwen estão sujeitos à licença do modelo.

## Cerebro central na Oracle Cloud

O Cerebro pode rodar como serviço central em uma VM Ubuntu da Oracle Cloud Infrastructure (OCI). O servidor precisa ter Ollama, o modelo escolhido, Node.js/npm e os plugins instalados. Clientes remotos precisam apenas deste projeto, Python 3 e conexão HTTPS; não precisam instalar Ollama, Node ou o modelo.

1. Crie uma VM Ubuntu ARM Ampere A1 (por exemplo, 4 OCPUs e 24 GB de RAM, se a cota/capacidade gratuita estiver disponível na sua região) ou outra VM que suporte o modelo. Free Tier e capacidade variam por região e podem mudar. Restrinja SSH ao seu IP e não abra as portas 11434 (Ollama), 8765 (Cerebro) nem serviços MCP para a internet.
2. Instale Ollama e Node.js/npm na VM e baixe o modelo central: `ollama pull qwen2.5:3b`. Clone o projeto em `/opt/cerebro`. Prepare o ambiente e os plugins como usuário do serviço:

   ```sh
   sudo useradd --system --create-home --home-dir /var/lib/cerebro --shell /usr/sbin/nologin cerebro
   sudo chown -R cerebro:cerebro /opt/cerebro
   sudo -u cerebro python3 -m venv /opt/cerebro/.venv
   sudo -u cerebro /opt/cerebro/.venv/bin/pip install -r /opt/cerebro/requirements.txt
   sudo -u cerebro npm install --prefix /opt/cerebro/.plugins --no-save --package-lock=false @modelcontextprotocol/server-filesystem@2026.8.31 @modelcontextprotocol/server-memory@2026.8.31 next-devtools-mcp@0.4.0 @modelcontextprotocol/server-github@2025.4.8 @googleworkspace/cli@0.22.5 @microsoft/workiq@1.0.1 apple-photos-mcp@2.1.20
   sudo -u cerebro env PLAYWRIGHT_BROWSERS_PATH=/opt/cerebro/.playwright-browsers /opt/cerebro/.venv/bin/python -m playwright install chromium
   ```
3. Copie `deploy/cerebro.service.example` para `/etc/systemd/system/cerebro.service` e `deploy/cerebro.env.example` para `/etc/cerebro.env`. Defina um segredo real e único com `openssl rand -hex 32`, proteja o arquivo com `sudo chmod 600 /etc/cerebro.env` e confira que `/opt/cerebro` e `/var/lib/cerebro` pertencem a `cerebro`. Se usar hubs, copie `config/hubs.example.json` para `/etc/cerebro/hubs.json`, configure os endpoints e credenciais no arquivo de ambiente protegido e mantenha chaves fora do JSON. Autentique o GitHub Copilot CLI como o usuário `cerebro`.
4. Para disponibilizar via internet, configure um domínio DNS apontando à VM, instale Caddy e adapte `deploy/Caddyfile.example` para seu domínio. Deixe acessíveis somente as portas 80/443 e SSH restrito; Caddy fornece HTTPS e encaminha para o serviço, que só escuta `127.0.0.1:8765`. Habilite o serviço com `sudo systemctl enable --now cerebro` e valide com `curl https://seu-dominio/health`.
5. Em cada computador cliente, clone o projeto e configure a URL e o mesmo segredo usado no servidor:

   ```sh
   export CEREBRO_SERVER_URL=https://seu-dominio
   export CEREBRO_API_TOKEN='seu-segredo-de-64-caracteres'
   ./cerebro remoto
   ```

   No PowerShell, defina `$env:CEREBRO_SERVER_URL` e `$env:CEREBRO_API_TOKEN` e execute `.\cerebro.bat remoto`. A conversa chega ao modelo da VM; pedidos de ação em navegador ou plugins aguardam aprovação interativa no terminal cliente.

Como alternativa sem expor uma API pública, conecte servidor e clientes a uma VPN privada como Tailscale e publique o serviço somente dentro da rede privada, mantendo HTTPS. O Cerebro central mantém conversas na memória do processo, então elas reiniciam junto com o serviço. O endereço e a configuração de rede devem ser providenciados na sua conta Oracle; não publique uma VM com token de exemplo. O Ollama não tem autenticação própria e fica vinculado ao loopback da VM. O serviço de exemplo roda o navegador em modo headless e desativa automação de desktop, que requer uma sessão gráfica real. Nesse modo, comandos de treinamento do Grindr via terminal remoto são reconhecidos pelo servidor, mas informam que o treinamento não foi ativado; para habilitá-lo, `CEREBRO_ENABLE_DESKTOP=1` deve ser configurado no servidor confiável que tem o ADB e o emulador acessíveis. Configurar essa variável apenas no cliente não habilita o monitor remoto.

## Ferramentas e permissões

- **Exemplo Python com LangChain e Ollama:** veja [`docs/langchain-ollama-example.md`](docs/langchain-ollama-example.md) para instalar as dependências, configurar um modelo com tool calling e executar ferramentas de arquivos e verificações locais com escopo restrito e aprovação.
- **Kit local de desenvolvimento:** `./.venv/bin/python -m pip install -r requirements-dev.txt` instala `pytest`/cobertura, Ruff, mypy e `pip-audit` apenas no ambiente virtual do projeto. `make check` executa compilação, lint, verificação de formatação, tipos e testes com cobertura; os alvos separados são `make build`, `make lint`, `make format-check`, `make typecheck` e `make test`. `make audit` consulta avisos de vulnerabilidade pela rede e requer aprovação como qualquer acesso externo. O workflow `.github/workflows/ci.yml` repete lint, tipos e testes em push/PR sem publicar deploy.
- **Ajuda interativa:** a inicialização exibe apenas a logo; use `/plugins` para consultar integrações e `/ajuda` para ver comandos. `/ajuda projeto|navegador|integracoes|terminal|seguranca|memoria` abre exemplos por tema. `/ferramentas` lista as ferramentas efetivamente disponíveis nesta execução; `/ferramentas projeto|terminal|navegador|desktop|mcp|local` filtra por categoria. Digite `/` para descobrir comandos. A lista não altera permissões: as aprovações existentes continuam valendo.
- **Desenvolvimento de software:** use `/projeto` no terminal para identificar a raiz ativa autorizada e os marcadores de projeto encontrados; o agente também tem `project_identify` para consultar essa informação antes de editar. O comando é informativo: não seleciona nem autoriza automaticamente outras pastas. O agente pode listar, ler, buscar texto literal (`project_search`), verificar sintaxe Python sem executar o código (`project_check_syntax`) e aplicar edições contextuais exatas (`project_apply_patch`) em arquivos dentro da raiz do projeto. O verificador aponta arquivo, linha e coluna; depois de corrigir erros relacionados ao trabalho, o Cérebro executa a verificação novamente e não deve alterar problemas preexistentes fora do escopo. `project_git_status` mostra branch, arquivos alterados e arquivos não rastreados; `project_git_diff` revisa diffs staged ou unstaged, no repositório da raiz ativa, sem alterar o índice. O agente usa status antes de editar e revisa o diff após mudanças. A busca limita arquivos, bytes e resultados, ignora dependências/cache e não segue links simbólicos; patches exigem que cada contexto apareça uma única vez e são gravados atomicamente. `terminal_execute` executa comandos não interativos e retorna a saída; `terminal_start`, `terminal_list`, `terminal_read`, `terminal_send` e `terminal_stop` iniciam e acompanham processos do projeto, como um servidor de desenvolvimento. Essa sessão não abre uma janela visível do Terminal. Processos são iniciados como argv separado, sem `shell=True`, em diretório validado dentro do projeto; a saída retida é limitada a 64 KiB, há no máximo oito processos simultâneos e os processos são encerrados ao terminar a aplicação. Iniciar, enviar entrada e encerrar processo exigem aprovação. Verificações de rotina (`unittest`, `pytest`, compilação Python, Ruff, mypy e verificações Git) podem rodar sem confirmação; instalações, downloads, acesso a serviços externos e deploy também pedem aprovação explícita. `project_run` continua disponível como nome compatível. Isso não é um sandbox: aprove somente comandos que você entende. No modo remoto, os processos rodam no servidor central, não no computador cliente.
- **Comandos no terminal:** `terminal_execute`, `project_run` e `terminal_start` aceitam argv em lista; por compatibilidade, também aceitam texto simples, que é separado em argumentos sem shell, expansão de variáveis ou encadeamento. Comandos não reconhecidos como verificações seguras ainda exigem aprovação.
- **Terminais remotos:** `remote_terminal_start` abre uma sessão gerenciada para um alias SSH VM já configurado em `~/.ssh/config` (`ssh-vm`) ou para Google Cloud Shell (`google-cloud-shell`). O Google Cloud Shell usa a conta/projeto ativo no `gcloud`; pode iniciar o ambiente, gerar/enviar uma chave pública SSH e incorrer custos. A conexão pede aprovação. Use `terminal_read`, `terminal_send` e `terminal_stop` com o ID da conexão; cada envio de linha é mostrado e pede aprovação. Em VMs, OpenSSH aplica as regras e o arquivo `known_hosts` padrão, sem desativar validação de host; configure e valide chave/host fora do Cerebro. No Cloud Shell, conexão e gerenciamento de chaves ficam a cargo do `gcloud`. A sessão oferece entrada/saída por linhas, não uma TTY local completa; programas de tela cheia, teclas de controle e fluxo de senha podem não funcionar. Credenciais não são solicitadas nem copiadas para a memória. Outros provedores Cloud Shell ainda não estão implementados.
- **Busca por nome:** `project_find_files` encontra arquivos por glob do nome (`*.tsx`, `*config*`) dentro da pasta autorizada, ignorando dependências, caches e links simbólicos e limitando a busca a 2.500 arquivos examinados e 100 resultados. Para buscar texto dentro dos arquivos, use `project_search`.
- **Skills do projeto:** o orquestrador descobre `SKILL.md` em `.github/skills/<nome>/` e `skills/<nome>/`, lista-as com `/skills` e seleciona no máximo três referências relevantes para cada tarefa. Só diretórios do projeto são examinados; links simbólicos são ignorados e cada Skill tem limites de tamanho. O conteúdo é tratado como referência não confiável, não concede permissões nem substitui as aprovações do runtime.
- **Navegador:** o Playwright integrado já está instalado e disponível como ferramentas `browser_*` do Cérebro; não é um servidor MCP separado e controla a própria sessão de navegador do assistente, não a tela de outros aplicativos. Use `browser_analyze_screen` após abrir uma página e depois de cada etapa para reconhecer prompts HTML, ler o texto visível e identificar controles habilitados; o agente pode então avançar passo a passo com cliques, preenchimento, teclas, espera e navegação, sujeito à aprovação das interações pelo runtime. Antes de clicar, o Playwright move visivelmente o ponteiro ao controle e pausa brevemente; cliques de desktop fazem o mesmo. A análise é estrutural, não interpreta pixels nem lê os valores digitados nos campos. Não contorne avisos de segurança nem submeta credenciais, códigos, pagamentos, formulários de alto impacto ou acordos legais em nome do usuário. Para responder mensagens, `browser_reply_message` exige seletores únicos da conversa/campo/botão e pede confirmação mostrando a página, o contexto da conversa e o texto exato; se a página ou conversa mudar após a confirmação, o envio é cancelado. Toques Android enviados via ADB não exibem o ponteiro do mouse do computador.
- **Uso remoto:** o navegador, a tela, o filesystem e MCP rodam no servidor central. As ações que alteram dados precisam de aprovação pelo terminal cliente conectado; navegador aberto e arquivos acessados são os do servidor, não os do computador cliente.
- **Controle da tela:** o agente de desktop pode capturar a tela e usar mouse/teclado; pedidos explícitos como “assuma o controle da tela” são encaminhados a esse agente. Cada ação de controle pede confirmação, e macOS pode exigir permissões de Acessibilidade e Gravação de Tela em Ajustes do Sistema. A captura atual é salva em `screenshots/tela-atual.png`; como o modelo padrão é somente texto, ele não interpreta pixels. Para identificar controles de uma página web, use `browser_analyze_screen`.
- **BlueStacks/Grindr:** instale Android Platform Tools, habilite ADB local nas configurações do BlueStacks (mantenha acesso ADB remoto desativado) e conecte manualmente o endpoint local da instância, por exemplo `adb connect 127.0.0.1:5685`. `desktop_android_list_inbox` procura automaticamente uma única instância emulada com Grindr em primeiro plano; se houver várias, pode receber `serial` explícito, que é validado quanto à conexão, emulador e Grindr ativo antes da leitura. Use `desktop_android_devices` para consultar seriais; não associe nomes de instância a seriais por suposição. A ferramenta abre a caixa de entrada se reconhecida e mostra OCR/controles. Apple Vision lê capturas em escala original e ampliada, conserva leituras conflitantes e mantém o limiar de confiança para ações; antes de tocar num resultado OCR, compara o tamanho da captura à resolução lógica declarada pelo Android. A digitação por ADB é limitada a caracteres ASCII imprimíveis; textos com outros caracteres são recusados no preview, antes de tocar no campo, para evitar rascunhos incorretos. Depois de abrir uma conversa, confirma o destinatário por um único cabeçalho acessível. O Cérebro lista os perfis e aguarda confirmação; evidência insuficiente de quem enviou resulta em direção ambígua, nunca em uma atribuição presumida. Mesmo após a confirmação inicial, cada conversa exige aprovação individual antes de ser aberta; cada envio exige aprovação separada do destinatário e do texto exato. O treinamento opcional, desligado por padrão, aprende somente categorias e estilos genéricos das trocas; nomes, mensagens e capturas não são persistidos. Se uma conversa indicar que recebeu foto ou outra mídia, não abra o conteúdo: considere apenas o texto já visível. Quando perguntarem de onde o usuário é ou de onde atende, a sugestão deve começar com `atendo sozinho na gloria ambiente discreto seguro confortavel`; quando perguntarem como está, deve começar com `na paz, pode perguntar`. A árvore de acessibilidade é lida de um XML temporário removido após a leitura. No macOS, Apple Vision faz OCR local da captura em memória; a captura não é salva e textos privados só são enviados ao Ollama em loopback, nunca a hubs/serviços remotos. O Kerberos não instala ADB, não conecta dispositivos e não inicia Grindr. A compatibilidade depende da versão do BlueStacks/Android e dos controles visíveis do Grindr. No modo remoto, ferramentas `desktop_*` ficam ocultas por padrão; habilite `CEREBRO_ENABLE_DESKTOP=1` apenas se o servidor confiável tiver acesso ao dispositivo desejado.

  Enquanto o Cérebro estiver aberto, `/grindr automatico ativar|desativar` controla a observação em segundo plano e a preparação de rascunhos para novas mensagens; `/grindr treinamento ativar|desativar` controla o aprendizado de padrões; `/grindr status` mostra os interruptores. Pedidos naturais como “quero que aprenda automaticamente formas diferentes de perguntas” também ativam somente o treinamento; ambos os modos começam desligados a cada inicialização. A observação consulta a cada 5 segundos apenas o chat já aberto ou prévias da caixa de entrada que já esteja visível no Grindr em primeiro plano no Android; não abre a caixa de entrada, não abre conversas nem visita outros perfis. Prévia não confirma direção: pode ser uma mensagem recebida ou enviada; quando o treinamento está ativo, serve somente para aprender sua categoria genérica, sem gerar rascunho ou guardar texto/nome. Conversas abertas podem ensinar pares mensagem/resposta genéricos apenas quando a direção está confirmada. Se o app não expuser um nome único no cabeçalho do chat, a mensagem visível pode ser identificada como perfil não identificado, mas nenhum rascunho é preparado até o destinatário estar identificável. Obter esse nome em layouts que o ocultam exigiria abrir o perfil, ação que o monitor não executa. Texto usado para preparar rascunhos vai diretamente ao Ollama em loopback, sem proxy nem redirecionamentos; se o Ollama não for local, o rascunho é recusado. Rascunhos nunca são enviados automaticamente: cada envio continua exigindo aprovação explícita. O treinamento identifica categorias e estilo por regras locais e guarda apenas rótulos genéricos no banco de aprendizado; não persiste nome, texto, hash de mensagem ou captura. Para pares de conversas abertas, se direção ou conversa não puderem ser identificadas pela acessibilidade, não aprende nem prepara rascunho. Ao desligar, resultados de chamadas já iniciadas são descartados; uma requisição local em andamento pode concluir antes de ser interrompida. O monitoramento para quando o Cérebro é encerrado.

  Com qualquer modo ativo, o terminal central mostra as instâncias emuladas autorizadas e conectadas ao ADB e indica em quais o Grindr está em primeiro plano, usando os nomes conhecidos do BlueStacks e o serial/porta como identificador seguro quando o nome configurado não puder ser consultado. O monitor só lê o chat ou a caixa de entrada que já estiverem visíveis; não abre conversas nem navega por perfis. Se o aplicativo ocultar o nome do perfil no cabeçalho do chat, mostra “perfil não identificado” em vez de confundir distância ou outro texto com um nome. Quando a caixa de entrada já estiver aberta, separa o nome do perfil da prévia visível e exibe ambos sem atribuir direção. Uma prévia não é tratada como recebida ou enviada: com treinamento ativo, sua categoria genérica é aprendida sem guardar texto/nome e sem abrir a conversa; prévias não geram rascunhos. Ao iniciar a observação de um chat já aberto, pode exibir uma única mensagem recebida visível mais recente; as demais mensagens anteriores não são reapresentadas. Mensagens novas observadas são exibidas como “Instância recebeu mensagem”, com nome da instância, serial, perfil, status da foto e conteúdo visível; rótulos da interface, como “Entregue”, “Cancelar envio” e chamadas para desbloquear confirmações de leitura, são filtrados para não aparecerem como mensagens. A foto só é marcada como ausente se essa condição estiver explicitamente exposta na árvore de acessibilidade, caso contrário aparece como não identificada. Cada instância é monitorada separadamente, mesmo quando várias estão com Grindr em primeiro plano, e uma falha de leitura em uma não interrompe as demais. O estado de observação é isolado por serial e mantido durante interrupções curtas ou enquanto o Grindr fica em segundo plano; ele é descartado ao desconectar a instância ou desligar os modos. Se não houver sobreposição inequívoca entre as mensagens já vistas e o snapshot atual, o monitor não atribui a mensagem como nova nem prepara rascunho naquele ciclo. A lista descreve apenas emuladores conectados/autorizados pelo ADB, não todas as janelas de emulador em execução. O texto privado não é gravado na base de aprendizado, mas é impresso no terminal e pode permanecer no scrollback, gravações ou logs do terminal.

  Os nomes de instância conhecidos são exibidos junto com o serial: `127.0.0.1:5645` como `Tiramisu64_9`, `127.0.0.1:5655` como `Tiramisu64_10` e `127.0.0.1:5685` como `Ipanema (Tiramisu64_13)`. Outros seriais locais recebem um rótulo de porta BlueStacks, sem inferir um nome configurado que o ADB não fornece.

- **Cibersegurança defensiva:** o Cérebro pode explicar redes e protocolos digitais, revisar código/dependências/configurações locais, sugerir hardening e apoiar laboratórios isolados e autorizados. Use `/seguranca` para ver esse escopo. Ele não concede superadmin nem privilégios persistentes, não varre redes sem autorização e não cria ou melhora malware. Operações seguem menor privilégio e as aprovações existentes; segurança absoluta não pode ser prometida. Pesquisa técnica atual é feita quando solicitada por meio de integrações configuradas, não como coleta contínua; não envie dados do projeto a serviços externos sem configuração e escopo explícitos.

### Cérebro Central: orquestração

O Cérebro Central é o runtime de orquestração que reúne o modelo local ativo, planejador, capacidades especialistas internas, ferramentas, memória e integrações configuradas. Especialistas como navegador, desktop e desenvolvimento são componentes que o Cérebro seleciona para uma etapa — não são o próprio Cérebro nem executores externos. O planejador escolhe uma capacidade, limita as ferramentas disponíveis nessa etapa e o runtime central executa localmente as chamadas autorizadas, devolve os resultados ao modelo e continua o ciclo até responder ou validar a tarefa. Argumentos inválidos e ferramentas fora da allowlist são recusados. Ações protegidas continuam sujeitas às confirmações descritas acima.

O modelo Ollama configurado é o runtime central padrão. Provedores e hubs externos são integrações opcionais; podem ser consultados segundo a configuração e o roteamento, mas não são necessários para executar ações locais. O hub Apple Intelligence usa o framework Foundation Models do macOS no mesmo computador do processo central; não substitui o Ollama, não executa ferramentas e não funciona no serviço Ubuntu/OCI. O sistema não pressupõe que vários modelos estejam ativos ao mesmo tempo. LangGraph implementa o fluxo de orquestração; `/ferramentas` lista as capacidades e ferramentas disponíveis.

### Aprendizado local compacto

O Cerebro pode guardar notas técnicas reutilizáveis somente depois de uma tarefa local de desenvolvimento que tenha aplicado uma edição e executado com sucesso uma verificação reconhecida (testes, lint ou type-check). A extração é uma única chamada curta ao Ollama local; falhas ou respostas inválidas não afetam a tarefa principal. O sistema não persiste transcrições, arquivos, diffs nem código bruto. Credenciais reconhecidas são redigidas antes da extração e as notas são sanitizadas, deduplicadas e limitadas a 100 entradas e 32.000 caracteres de texto.

Notas recuperadas são injetadas como dados de referência não confiáveis, nunca como políticas ou permissões; alterações futuras continuam sujeitas ao fluxo normal de revisão e validação, sem autoedição baseada em memória. Isso permite reaproveitar práticas e comandos de desenvolvimento somente após uma edição local e uma verificação reconhecida bem-sucedidas; não armazena histórico bruto nem executa comandos aprendidos automaticamente. Use `/aprendizado` para inspecionar as notas e o uso, e `/aprendizado apagar` para removê-las após confirmação. Os limites se aplicam ao conteúdo de notas, não garantem um limite físico para o arquivo SQLite que também mantém o histórico operacional local.

Históricos legíveis já salvos no VS Code e no Codex também podem ser importados como referências de conversas, executando na raiz do projeto: `python3 -m assistente.import_history`. Para incluir, além das mensagens, os pedidos, respostas finais, chamadas de ferramentas, comandos, resultados e códigos de saída dos rollouts de um projeto, informe o nome exato da pasta: `python3 -m assistente.import_history --project-name www-italosantos-com`. O importador inclui rollouts sob `~/.codex` cujo diretório de trabalho termine exatamente nesse nome, inclusive cópias locais e worktrees reconhecidos nos metadados do Codex; não segue arquivos externos à pasta local do Codex. Dados de eventos são mantidos comprimidos no banco; a busca indexa trechos limitados, e somente os campos/textos que correspondem a padrões conhecidos são redigidos. Saídas sem um código de saída ou status explícito permanecem classificadas como desconhecidas, mesmo se contiverem palavras como “error”. A importação não altera os arquivos de origem, não acessa a rede e pode ser repetida para atualizar registros; o banco fica em `CEREBRO_DATA_DIR/history/training.sqlite3` (por padrão `~/.local/share/cerebro/history/`), com permissões somente do usuário no macOS/Linux. O Cérebro recupera no máximo três trechos e 5.000 caracteres para tarefas locais de código; quando a tarefa menciona `www-italosantos-com` ou `italosantos.com`, prioriza histórico e eventos de rollouts com esse nome de pasta. Todo o histórico é dado não confiável; comandos antigos nunca concedem autorização. Os filtros de credenciais são baseados em padrões e não garantem a remoção de todo dado sensível. O Codex App pode manter outros dados `.data` opacos que não são importados. Isto não retreina os pesos do modelo: disponibiliza exemplos relevantes ao modelo local no contexto de cada tarefa. Execute o importador novamente para incorporar conversas novas.

### RAG local para fontes oficiais

O Kerberos pode indexar sob solicitação páginas públicas de uma lista fixa de fontes técnicas oficiais: Apple, Microsoft, Android, Ubuntu, CISA, NIST (firmware, criptografia pós-quântica, WLAN, Bluetooth, RFID, LTE e IoT) e ITU-R (propagação para enlaces ópticos terrestres em espaço livre). `/rag fontes` lista as URLs; `/rag indexar <nome>` baixa uma página e sempre pede aprovação antes do acesso à rede; `/rag buscar <consulta>` pesquisa os trechos locais; `/rag` mostra o estado e `/rag apagar` remove o índice após confirmação. O modelo também pode usar `rag_search` e propor a indexação de uma fonte permitida, que ainda depende de aprovação humana.

O índice fica em `CEREBRO_DATA_DIR/rag.sqlite3`, separado do banco de execução, com permissão privada em sistemas POSIX. Guarda texto extraído, URL, título e data de indexação até exclusão explícita; portanto, **não é efêmero**. A busca atual é lexical SQLite FTS5, não busca vetorial/semântica; isso não retreina o modelo nem cria conhecimento autônomo. A lista é restrita a hosts oficiais exatos, HTTPS, sem credenciais, IPs, endereços privados ou redirecionamentos. Respostas recuperadas são dados não confiáveis: o modelo deve verificar alegações e citar a URL/data; texto de uma página não altera políticas nem permissões. O coletor não segue links nem descobre fontes automaticamente. NotebookLM não possui API pública documentada para ingestão direta; o conector MCP disponível é comunitário e usa interfaces/endpoints internos não documentados. Conectores BigQuery, Databricks, Snowflake, AWS, Azure ou Google Cloud ainda não estão implementados; cada conector exigiria escopo de conta/dataset e identidade read-only específicos. A recomendação ITU-R indexada trata de propagação para enlaces ópticos terrestres em espaço livre; não é um guia de espionagem, interceptação ou configuração tática de infravermelho. O catálogo de cibersegurança e IA inclui páginas selecionadas do NIST, OWASP, Google SAIF e Microsoft AI Red Team; é uma curadoria fechada de conteúdo público e defensivo, não “tudo” sobre o tema, e não habilita descoberta automática de fontes ou instruções de ataque.

### Hubs externos opcionais

O planejador do Cérebro Central escolhe a capacidade local apropriada. Quando houver hubs habilitados, o orquestrador pode enviar pedidos não relacionados à execução local do projeto a todos eles em paralelo e fornecer as respostas ao modelo local para síntese. Pedidos de código e ações no projeto não são enviados aos hubs. O Cérebro não envia histórico de conversa nem arquivos do projeto aos hubs; padrões comuns de tokens e senhas são removidos antes do envio, mas isso não detecta todo dado confidencial. Não inclua segredos nem dados sensíveis em tarefas destinadas a serviços externos. Respostas externas são tratadas como conteúdo não confiável e não recebem permissão para executar as ferramentas locais do Cérebro.

Cada serviço exige configuração e autenticação próprias; login no GitHub não libera automaticamente modelos de outros serviços. O acesso a OpenRouter, CrewAI AMP e serviços hospedados pode gerar custos. Consulte os limites/preços do serviço antes de habilitá-lo.

Se o MCP do GitHub retornar limite de requisições — incluindo respostas temporárias 429 e limites secundários — o Cerebro encerra e remove as rotas, remove a autenticação local do `gh` e grava um bloqueio persistente em `CEREBRO_DATA_DIR`. Reinícios e credenciais GitHub legadas no JSON não reconectam o plugin; somente `/mcp login github` após autenticação explícita libera uma nova conexão. O plugin usa exclusivamente o token obtido por `gh auth token`, não tokens estáticos no JSON ou no ambiente. O `gh auth logout` remove a credencial apenas deste computador e **não revoga o token no GitHub**; revogação remota de tokens do GitHub CLI deve ser feita em [GitHub Settings → Applications](https://github.com/settings/applications).

Nos hubs `openai_compatible` e `crewai_amp`, é possível configurar várias credenciais independentes no campo `accounts`. O Cerebro tenta a próxima credencial configurada somente quando o provedor responde HTTP 401; não alterna contas em HTTP 429, erros de quota, nem em falhas genéricas. Cada hub mantém sua própria lista de contas. Isso é failover de credenciais autorizadas, não renovação de cotas nem criação de tokens. A renovação OAuth ou de chaves continua sendo responsabilidade do CLI/serviço oficial. Não use credenciais para contornar limites ou termos do provedor. Endpoints autenticados exigem HTTPS; HTTP é permitido apenas em loopback local. Redirecionamentos HTTP são recusados para impedir o encaminhamento de credenciais a outro host.

1. Copie `config/hubs.example.json` para `~/.config/cerebro/hubs.json` e habilite apenas os hubs que já configurou. O caminho pode ser substituído por `CEREBRO_HUBS_CONFIG`.
2. Configure as credenciais no ambiente do terminal — nunca grave chaves no JSON:

   - **GitHub Copilot CLI:** execute `copilot login` antes de iniciar o Cerebro ou use `/login-copilot` durante uma conversa para iniciar o fluxo OAuth oficial de navegador do CLI (`copilot login --web-flow`). O Copilot captura o callback loopback e armazena a credencial pelo mecanismo seguro dele; o Cerebro não implementa nem armazena tokens OAuth. O CLI oficial pode deixar a página aberta após autenticar e não oferece ao Cerebro uma referência segura à aba para fechá-la; feche-a manualmente. Uma conta GitHub, sem acesso ao Copilot, não habilita o serviço. Use `/copilot-uso` para abrir o CLI autenticado: `/statusline quota` mostra a cota restante do plano (créditos de IA ou requisições premium, conforme o modelo de cobrança) e `/usage` mostra o consumo da sessão atual. O Cerebro não consulta diretamente a cota da conta porque o CLI não expõe esse dado em sua interface de automação. Para chamar um agente personalizado, configure o hub em `hubs.json`, por exemplo:

     ```json
     {
       "name": "copilot-reviewer",
       "enabled": true,
       "type": "copilot_cli",
       "command": "copilot",
       "agent": "reviewer",
       "agent_dir": "/caminho/para/o/projeto-com-agentes",
       "model": "auto"
     }
     ```

     O nome deve corresponder ao agente em `.github/agents` dentro do diretório informado. Se os agentes estiverem no diretório atual onde o Cerebro é iniciado, `agent_dir` pode ser omitido. O Copilot é executado sem permissão para usar ferramentas (`--deny-tool "*"`) e recebe somente a tarefa atual, não o histórico nem arquivos do projeto. Hubs externos podem transmitir suas tarefas para serviços em nuvem; habilite apenas se estiver de acordo com essa transmissão.
   - **Rotação de contas do Copilot:** não é automática; altere a conta pelo fluxo oficial do CLI. O CLI continua responsável pela renovação e armazenamento seguro do OAuth.
   - **OpenRouter:** defina `OPENROUTER_API_KEY` e substitua `YOUR_OPENROUTER_MODEL` por um modelo disponível na sua conta.
   - **OpenHands local/hospedado:** configure o agente-server com gateway OpenAI compatível, URL `/v1`, nome do perfil e chave de sessão próprios.
   - **CrewAI AMP:** use a URL e o bearer token do crew implantado; ajuste `inputs` às entradas obrigatórias desse crew.
   - **AutoGen Studio:** instale `autogenstudio` no ambiente Python indicado em `python` e aponte `team_config` para uma equipe exportada do Studio.
   - **Apple Intelligence local (Mac):** habilite `"enabled": true` no hub `apple-intelligence` já presente no exemplo. Requer o processo central rodando como usuário em um Mac Apple Silicon compatível, macOS 26 ou posterior, Swift/Xcode Command Line Tools e Apple Intelligence habilitado e disponível no sistema. O Cérebro consulta a disponibilidade em cada chamada; o modelo é executado localmente pela Foundation Models e recebe apenas a tarefa atual já sanitizada. Não requer chave ou serviço web. Este hub não instala/ativa Apple Intelligence no macOS e não funciona na VM Ubuntu da OCI; nesse caso seria preciso hospedar o runtime central em um Mac compatível. As respostas locais ainda passam pela regra geral: outros hubs remotos que você habilitou também podem receber a mesma tarefa.

   Exemplo de duas contas no mesmo hub (substitua `api_key_env` por variáveis distintas configuradas no ambiente):

   ```json
   {
     "name": "openrouter",
     "enabled": true,
     "type": "openai_compatible",
     "base_url": "https://openrouter.ai/api/v1",
     "model": "SEU_MODELO",
     "accounts": [
       {"name": "principal", "api_key_env": "OPENROUTER_KEY_PRIMARY"},
       {"name": "reserva", "api_key_env": "OPENROUTER_KEY_BACKUP"}
     ]
   }
   ```

   `accounts` aceita de 1 a 10 contas; quando presente, substitui `api_key_env`. Os estados exibem somente quantas credenciais estão configuradas. Hubs antigos com um único `api_key_env` continuam compatíveis.

3. Inicie `./cerebro` e use `/plataformas` para listar GitHub Copilot CLI, Apple Intelligence, OpenHands, OpenRouter, CrewAI AMP e AutoGen Studio; `/hubs` mostra os hubs habilitados e seu estado. No modo remoto, `/hubs` consulta a configuração do servidor central; defina as credenciais e faça login nos CLIs no ambiente desse servidor. Hubs sem credenciais ou com endpoints indisponíveis mostram erro, sem impedir a resposta local do Ollama.

Hubs externos podem executar seus próprios agentes e ferramentas no ambiente deles. Em particular, o gateway OpenHands executa o ciclo do agente configurado no servidor; limite o workspace e as ferramentas desse serviço. Para não enviar tarefas à nuvem, deixe os hubs desabilitados no JSON.

## Edição de imagens gratuita no Mac

Também é possível instalar o **ComfyUI Desktop** (geração e edição generativa com modelos locais) e o **GIMP** (edição tradicional gratuita). No Mac Apple Silicon, abra pelo Spotlight ou pelo Terminal:

```sh
open -a "Comfy Desktop"
open -a GIMP
```

No ComfyUI, faça a configuração inicial e baixe um modelo compatível para habilitar geração, image-to-image e inpainting; os modelos podem ocupar vários GB e são baixados separadamente. O ComfyUI é gratuito, mas os termos de uso variam por modelo. O GIMP não exige modelo e serve para recortes, ajustes, camadas e retoques manuais. Eles são aplicativos separados e não são chamados automaticamente pela conversa do `cerebro`.

## Perfis locais para testes

Para manter os dados locais do Cerebro separados entre execuções de teste autorizadas, inicie cada processo com um identificador fixo de workspace:

```sh
CEREBRO_WORKSPACE=qa-a ./cerebro
CEREBRO_WORKSPACE=qa-b ./cerebro
```

No PowerShell, defina `$env:CEREBRO_WORKSPACE = "qa-a"` antes de iniciar `.\cerebro.bat`. O nome aceita somente letras minúsculas, números e hífens internos, até 40 caracteres; valores inválidos impedem a inicialização. Sem essa variável, os caminhos existentes permanecem inalterados.

Cada perfil usa diretórios próprios para o banco de auditoria e memória em `CEREBRO_DATA_DIR/workspaces/<nome>/data`, além de `mcp.json` e `hubs.json` próprios, colocados em subdiretórios `workspaces/<nome>` ao lado dos caminhos de configuração usuais. As configurações por perfil não são herdadas das configurações pessoais compartilhadas. No servidor remoto, o perfil é definido no processo do servidor, não por uma requisição individual; instâncias que precisem de separação entre clientes também devem usar credenciais de serviço distintas.

Isso é **separação de dados gerenciados pelo Cerebro, não isolamento total de ambiente ou de contas**. O processo ainda pode herdar as mesmas variáveis de ambiente e credenciais; o plugin de arquivos e o desktop/navegador continuam no mesmo usuário e projeto; cache de modelos e efeitos em serviços externos também não são separados. Para isolamento forte, execute cada ambiente em contêiner/VM ou conta de sistema operacional distinta, com diretório de projeto, perfil de navegador, credenciais de sandbox e permissões próprios. Use somente contas e sandboxes autorizados pelos provedores; perfis não criam identidades, não alternam logins nem renovam períodos de avaliação.

## Por que LangGraph

LangGraph coordena ciclos de planejamento e execução: o modelo pode chamar uma ferramenta, avaliar o resultado e continuar com a próxima etapa, até concluir ou atingir o limite de segurança de iterações. As integrações com CrewAI AMP e AutoGen Studio são opcionais; LangSmith e Phoenix não são usados.

## Runtime local: contexto e auditoria

O runtime mantém o histórico recente limitado a 60 mil caracteres serializados, descartando turnos antigos completos sem quebrar uma sequência atual de chamadas e resultados de ferramentas. A instrução de cada agente é enviada apenas à chamada atual do modelo, para não crescer repetidamente no histórico.

Cada execução local ou remota recebe um ID e gera eventos estruturados de roteamento, seleção de agente, chamada de ferramenta e conclusão/falha. O banco `runtime.sqlite3` fica em `CEREBRO_DATA_DIR` (por padrão, `~/.local/share/cerebro` no modo local; no serviço, `/var/lib/cerebro`) e registra somente metadados: não grava prompts, argumentos, conteúdo retornado pelas ferramentas nem mensagens de erro. Em sistemas POSIX, o arquivo é criado com permissão privada. Use `/execucoes` no terminal para consultar as execuções recentes; no servidor, `GET /v1/runs` e `GET /v1/runs/{id}/events` exigem o token Bearer.

### Estado operacional e recuperação

O mesmo banco SQLite mantém uma identidade operacional mínima (`agent_id`, nome, data de criação e ID da última execução concluída como checkpoint); isso representa estado persistido, não consciência. O SQLite já usa transações como journal de recuperação de operações interrompidas, então não é mantido um journal de texto separado. Após alterações, o runtime atualiza atomicamente um único snapshot adjacente (`runtime.sqlite3.bak`) e usa um pequeno arquivo `.lock` para sincronizar o acesso entre instâncias.

Na inicialização, o Kerberos valida o banco com `quick_check` e restaura o snapshot se o banco principal estiver ausente ou corrompido. Se ambos forem inválidos, ou houver sidecars SQLite que possam indicar outra instância ativa, o programa falha explicitamente e preserva os arquivos para recuperação manual. O snapshot é um ponto de recuperação recente, não histórico ilimitado; uma falha entre a confirmação de uma transação e a atualização do snapshot pode perder essa última alteração. Excluir o banco e o snapshot remove os dados intencionalmente, e nenhum mecanismo tenta impedir a desinstalação ou a exclusão pelo usuário. Para proteção contra falha de disco ou perda de todo o perfil, mantenha backup externo sob controle do usuário.

O runtime não desativa warnings globalmente: avisos devem ser corrigidos na origem ou tratados de forma específica para não esconder problemas reais.

Chamadas ao Ollama podem repetir até três vezes em erros transitórios de rede ou HTTP 408/429/5xx. Chamadas de ferramentas não são repetidas automaticamente, pois uma ação pode ter sido concluída mesmo quando houve timeout. O runtime não configura provedores externos nem adiciona fontes RAG: esses serviços dependem de endpoints, credenciais e fontes escolhidas pelo usuário. Scheduler/fila persistente, sandbox de sistema operacional, gestão de segredos externa, alertas, métricas de custo, CI/CD e rollback de produção também não são instalados por esta configuração local.

## Acesso por celular

O modelo roda no computador, não no iPhone ou Android. Um aplicativo compatível com Ollama no celular pode conectar-se ao computador pela rede local, desde que o Ollama esteja configurado para aceitar conexões remotas. Não exponha a porta do Ollama diretamente à internet: ela não oferece autenticação por padrão. A CLI e os plugins deste projeto rodam no computador.
